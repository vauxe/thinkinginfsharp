# 第 35 章答案 {#overview}

这些答案把兼容性、文件替换与资源生命周期作为三项独立策略。迁移不只是“加入可空字段”，刷新不等于事务，依赖注入也不会决定谁负责释放借用的客户端。

## 练习 1：演进快照契约 {#exercise-01}

### 先分派版本，再进行严格的版本专属解析 {#exercise-01-dispatch}

保持当前 `BookingDto` 的版本 1 格式不变。另建 `BookingDtoV2`，保留已有字段，再加入 `[<JsonPropertyName("customerNote")>] CustomerNote: string | null`。已有文件写出后，不能再改变 `schemaVersion = 1` 的含义。

读取分为六步：

1. 应用已有字节上限、严格 UTF-8 解码与 JSON 深度限制。
2. 用 `JsonDocument` 或最小封装对象仅读取顶层 `schemaVersion`。
3. 把 `1` 分派给版本 1 专用的反序列化器与映射器。
4. 把 `2` 分派给独立配置的严格版本 2 反序列化器与映射器。
5. 对其他每个整数返回 `UnsupportedSchemaVersion actual`。
6. 版本缺失或不是整数时，返回数据损坏错误。

必须先分派版本，再严格反序列化完整对象。否则版本 2 的 `customerNote` 会被版本 1 选项当成未知成员，并以错误原因失败。

采用以下兼容性表：

| 已存文档 | 内存结果 | 重写策略 |
|---|---|---|
| 完整匹配版本 1 | 已验证预约加 `CustomerNote = None` | 加载期间不写入 |
| 没有 `customerNote` 的版本 2 | 已验证预约加 `None` | 稍后保存为规范版本 2 |
| 带字符串备注的版本 2 | 已验证预约加 `Some note` | 下次成功保存时保留 |
| 带未知成员的版本 2 | 严格策略下的损坏/不支持表示 | 不修改文件 |
| 版本 3 | `UnsupportedSchemaVersion 3` | 不猜测，也不降级 |

读取时只在内存中升级；下一次业务保存成功时再重写。读取不应意外写入、引入新的失败方式或改变时间戳。若运维确实要求立即迁移，应提供带备份、审计与回滚的独立命令。

备注仍需明确领域规则。“可选”只说明它可以缺失，没有说明最大长度、空白处理、隐私要求，甚至没有说明备注是否属于预约。写明这些规则后，才能加入经过验证的领域类型。

契约测试应保留全部版本 1 快照测试，并加入版本 2 的完整序列化形式。确认两个版本都能映射到预期的已验证值。还要确认版本 3 与未知成员会在文档规定的阶段失败。

## 练习 2：审计每个保存中断点 {#exercise-02}

### 分开目标可见性与持久性 {#exercise-02-table}

假设已经有一个旧完整目标：

| 中断点 | 读者可见的目标 | 临时文件 | 可以保证什么 |
|---|---|---|---|
| 创建临时文件前 | 旧完整目标 | 无 | 写入尚未开始 |
| 写临时文件期间 | 旧完整目标 | 可能不完整 | 正常展开会删除；进程崩溃可能留下残留 |
| `Flush(true)` 后、移动前 | 旧完整目标 | 完整暂存字节 | 取消会删除；崩溃可能留下完整残留文件 |
| 同卷替换期间 | 文件系统专属的旧或新替换行为 | 正在重命名 | 没有原地写入部分目标 |
| 成功移动后 | 新完整目标 | 通常不存在 | 提交已经发生；稍后的取消无法撤销已可见结果 |

实现会在写入前检查取消，并在 `File.Move` 前再次检查。移动后不再执行可取消的等待。如果令牌在提交后并发取消，仍应返回 `Ok`，因为结果已经可见。

必须区分三项保证：

- 读者可见的替换：通过同目录移动替换目标，不逐字节覆盖原文件。
- 缓冲区刷新：`Flush(true)` 请求在移动前写出中间文件缓冲区。
- 断电持久性：文件数据、重命名元数据与目录项是否持久，取决于操作系统、文件系统、挂载选项与设备行为；本例没有证明它。

`finally` 中的清理属于尽力而为。启动维护程序可以先确认文件不是已配置目标，再删除符合私有临时命名模式的旧文件。它绝不能删除宽泛目录，也不能接受未验证路径。

如果需求是“预约与支付授权一起提交”，无论怎样重排这七个文件步骤都无法提供保证。它需要更宽的一致性协议，而不是为 `File.Move` 使用更强措辞。

## 练习 3：明确改变资源释放责任 {#exercise-03}

### 区分借用的能力与自行管理的资源 {#exercise-03-borrowed}

重构组合，让它依赖能力而不是具体替身：

```fsharp
type ExternalServicePorts =
    { Charge: PaymentRequest -> CancellationToken -> Task<PaymentOutcome>
      Notify: NotificationRequest -> CancellationToken -> Task<unit> }

type BorrowedInfrastructureComposition =
    inherit IDisposable
    abstract member Ports: AsyncPorts

val startBorrowed:
    configuration: BookingStoreConfiguration ->
    externalServices: ExternalServicePorts ->
    getUtcNow: (CancellationToken -> Task<DateTimeOffset>) ->
    BorrowedInfrastructureComposition
```

这份 `.fsi` 风格声明表达接口契约，不代表本章适配器已经实现它。生产实现会把现有端口记录的构造放到 `startBorrowed` 内部。借用型组合也不会暴露具体的 `PaymentStub` 或 `NotificationStub` 属性。

宿主创建长生命周期客户端、注册它们、启动一个或多个借用型组合，并在释放共享客户端之前先释放各组合。如果客户端实现 `IAsyncDisposable`，宿主会在自己的关闭边界等待它们。借用型组合绝不能调用任一释放接口。

不要使用含糊的 `ownsClients: bool` 标志。应提供不同的构造函数或类型，例如演示使用 `startOwnedStubs`，宿主客户端使用 `startBorrowed`。调用位置由此直接表明谁负责释放客户端。

释放后使用分成两层：

1. 每个组合仍把自身标记为关闭，并拒绝新端口调用。
2. 宿主保证只要还有借用型组合处于活动状态，就不释放共享客户端。

测试仍可保持确定性。先在测试中创建 `PaymentStub` 与 `NotificationStub`，再把它们的 `Invoke` 函数作为借用能力传入。替身由测试最外层的 `use` 作用域释放。测试应覆盖授权、拒绝、指定故障，以及预先取消时不记录调用。还要确认释放组合不会释放借用的替身。

调用方令牌仍须原样传递。借用只改变释放责任，不允许组合替换取消、重试或错误策略。

## 答案回顾 {#solution-review}

- 保留每个已写出模式版本的原有含义。
- 应先检查版本，再应用严格的版本专属未知成员规则。
- 读取时只在内存升级；立即重写应成为单独的迁移操作。
- 可选字段仍然需要领域与隐私策略。
- 移动前，旧目标仍是当前版本；移动后，提交已经发生。
- 临时清理与崩溃恢复是不同关注点。
- 刷新会请求持久化缓冲区，但不能保证所有环境下都能抵御断电。
- 文件替换无法把远程支付操作一并原子提交。
- 借用的服务能力与自行管理的资源需要不同构造 API。
- 创建者/宿主会在每个借用方关闭后释放共享客户端。
- 测试把确定性替身作为借用函数传入时，它们仍然有用。
- 改变释放责任不会改变取消或失败语义。
