# 第 45 章练习答案 {#overview}

这些是工程解答，而不是唯一有效代码。好的答案会先明确语义，再选择语法或包；保留清单脚本的已有证据，并把资料研究与已执行证明分开。

## 练习 1：增加排除规则而不失确定性 {#exercise-01}

“glob”一词并不是完整契约。Shell 和库对于分隔符、大小写、隐藏文件、字符类、递归匹配、畸形模式，以及目录匹配是否剪枝遍历，意见并不一致。添加 `--exclude` 前应先定义这些决策。

### 契约 {#exclusion-contract}

一种可接受的版本 2 契约是：

- `--exclude PATTERN` 可以在模式之后、两个位置路径之前重复；
- 模式和候选路径不论宿主 OS 都使用 `/`；
- 匹配在所有平台上均采用 ordinal 且区分大小写；
- `*` 匹配一个路径段内零个或更多字符；
- `?` 恰好匹配一个非 `/` 字符；
- `**` 只有作为完整路径段时才有效，并匹配零个或更多完整路径段；
- 不支持并拒绝 `[abc]`、brace 展开、转义、绝对路径、空段、`.` 段与 `..` 段；
- 模式命名文件；排除目录树要显式写 `logs/**`；
- 在评估用户规则前，先按身份排除输出文件；
- 符号链接仍按现有遍历策略跳过，与排除规则无关；
- 重复模式会被删除，再对规范化模式按 ordinal 排序；
- 无效模式在哈希或写入前失败，并作为用法错误返回退出码 `2`。

始终区分大小写可能让 Windows 用户意外，但它能产生一份统一仓库契约。另一答案也可以有意遵循文件系统大小写规则，只要记录并测试这种依平台而异的行为。

### Schema 与规划 {#exclusion-schema}

应升级清单版本，因为排除规则改变了“完整”的含义：

```json
{
  "schemaVersion": 2,
  "exclusions": ["**/*.pdb", "logs/**"],
  "files": []
}
```

纳入规范化规则后，即使两份清单当前具有相同文件行、未来覆盖范围不同，也能区分。评审者也能看到产物为何缺失。

从概念上把规划边界重构为：

```text
解析参数
  -> 验证并规范化模式
  -> 枚举但不跟随链接
  -> 规范化每个相对路径
  -> 应用排除规则
  -> 对纳入文件计算哈希并排序
  -> 渲染一份版本 2 期望文档
```

`write` 与 `check` 必须调用同一个规划器。独立检查实现很容易漂移。把输出文件排除放在用户模式之外，使调用者无法意外让清单哈希自身。

目录剪枝是一项带语义风险的优化。`logs/**` 规则可以安全剪掉 `logs`，但带否定或未来 include 规则的通用匹配器可能仍需下降。该契约没有否定，所以经过测试的前缀分析可以剪枝；第一版可保持简单，在遍历后过滤文件路径。

### 匹配器选择 {#matcher-choice}

不要把任意用户模式直接翻译成无界正则表达式。要么用线性路径段匹配器只实现上述语法并限制模式长度，要么针对精确语义评估受维护 glob 包。

本答案只有在验证性试验（spike）证明以下全部条件后才选择包：

- 支持显式 ordinal、区分大小写比较；
- `**` 与分隔符规范化符合书面契约；
- 畸形模式可以在文件系统效果前拒绝；
- 遍历仍受清单脚本的链接与根策略控制，而不是让库自行行走；
- 包目标与传递图适合升级后的控制台项目；
- 锁文件与锁定还原能复现该图。

若没有候选满足这些约束，有意缩小的语法比宣称完全 glob 兼容更安全。把它命名为“产物模式语法”、写出文档，并拒绝不支持的语法，而不是近似模拟 shell。

### 测试矩阵 {#exclusion-tests}

同时使用纯路径/模式测试与真实临时目录：

| 情形 | 期望证据 |
|---|---|
| 无规则 | 版本 2 包含与清单脚本相同的两个文件 |
| `**/*.pdb` | 嵌套和根 `.pdb` 文件缺失；`.PDB` 仍存在 |
| `logs/**` | 规范化 `logs/` 下所有文件均缺失 |
| `a/?eta.bin` | `a/beta.bin` 匹配；`a/longbeta.bin` 不匹配 |
| 不同输入顺序中的重复规则 | 规范化 JSON 与摘要行逐字节相同 |
| 模式中出现反斜线 | 用法失败发生在输出变更前 |
| `../secret` 或绝对模式 | 验证拒绝路径穿越语义 |
| 输出位于源内 | 即使没有规则命名它，输出仍被排除 |
| 第二次写入 | `Unchanged` 且哨兵时间戳不变 |
| 过期检查 | 退出 `2`，不写入，原输出字节不变 |
| 指向树外的链接 | 链接被跳过；永不哈希外部文件 |

在每个 OS 上的纯测试中模拟 Windows 风格字符串，再在真实 Windows 与类 Unix runner 上增加文件系统测试。不要把仅 Linux 路径测试称为跨平台证据。

## 练习 2：编写包采用记录 {#exercise-02}

从需求而不是候选开始。升级工具需要 `write` 与 `check` 子命令、两个必需路径参数、可重复 `--exclude`、生成帮助、可预测用法失败、无需终止进程即可测试的解析，以及普通 .NET 10 发布。Shell 补全与原生 AOT 是期望项，但不是发布要求。

### 截至 2026-08-25 的候选记录 {#candidate-record}

为本答案核对的 NuGet 官方页面显示：

| 选择 | 核对版本 | 相关形状 | 摩擦或尚无证据之处 |
|---|---:|---|---|
| 手写解析器 | 仓库代码 | 当前零包图；精确控制三个 token | 帮助、重复选项、别名、诊断与未来子命令变成我们的维护责任 |
| Argu | 6.2.5 | 面向 F#、使用可辨识联合的声明式解析器；目标为 .NET Standard 2.0 | 包最后更新于 2024 年 12 月；引入 FSharp.Core 与 `System.Configuration.ConfigurationManager`；裁剪/AOT 行为需要真实试验 |
| System.CommandLine | 2.0.11 | 命令、选项、参数、验证、帮助、补全与异步 action；目标为 .NET 8 和 .NET Standard 2.0 | object/builder API 偏 C#；F# 重载/null 适配以及精确帮助/错误稳定性需要试验 |

两个包版本都是在该日期核对的研究事实，不是本仓库已编译的包。清单脚本的自动证据仍只覆盖脚本中的 BCL 解析器。

不要像比较正确性那样比较下载量。应检查所有者、MIT 许可证、源码仓库、依赖标签、发布历史、公告与精确 `.nupkg`，再在仓库有效包源下运行还原审计。

### 聚焦试验 {#parser-spike}

为每个包创建可丢弃的 `net10.0` F# 控制台项目。锁定精确直接版本与生成闭包。让解析器作为近似纯适配器，把 `string array` 转成：

```fsharp
type Command =
    | Write of source: string * output: string * exclusions: string list
    | Check of source: string * output: string * exclusions: string list
    | ShowHelp

type ParseFailure =
    { ExitCode: int
      StandardError: string }
```

库专属类型停在该适配器内。清单规划只接收 `Command`。这样移除包时不必触碰哈希、schema 或文件系统策略。

针对手写解析、Argu 与 System.CommandLine 运行相同黄金向量：

- 有效 `write` 与 `check`，分别带零、一和三项排除；
- 若契约允许，选项分别位于位置参数前后；
- `--help`、未知选项、缺少源、重复不可重复选项与无效模式；
- `--` 终止符后以 `-` 开头的路径；
- 作为已分隔参数 token 传入的 Unicode 与含空格路径；
- 精确退出类别与目标流，同时允许规范化有意不稳定的装饰文本；
- 在 Windows 与一个类 Unix 目标调用发布的可执行程序；
- 只有当裁剪与原生 AOT 成为声明发布要求时才验证它们。

捕获还原、锁 diff、构建警告、包审计、发布大小、启动与适配器代码量。不要从目标框架兼容性推断 AOT 支持。

### 可逆决策 {#package-decision}

清单脚本当前契约只有一个模式与两个路径，因此保留手写解析器。对于带可重复排除和生成帮助的升级工具，如果试验通过所有向量，则暂定选择 System.CommandLine `2.0.11`。其命令模型符合规划 CLI，而且最近稳定版本有直接 .NET 所有权路径。

这不是对 Argu 的普遍偏好。如果团队重视以 DU 声明的 F# 表面，且其试验用可接受的维护与部署证据产生更清晰代码，就选择 Argu。决定性产物是适配器与测试矩阵，不是语言品牌。

采用变更应包括：

- 控制台项目中的精确 PackageReference；
- 已提交 `packages.lock.json` 与 CI `dotnet restore --locked-mode`；
- 有效包源与 Package Source Mapping 评审；
- 依策略处理警告的还原审计；
- 一个拥有所有包专属类型的模块；
- 黄金 CLI 契约测试与发布后进程冒烟；
- 更新负责人和季度评审触发器；
- 一份移除说明：只替换解析适配器，保留 `Command` 与全部核心函数。

若包未通过某项必需向量，就保留手写解析或试验另一候选。不要为了符合库默认值而扩张公开 CLI。

## 练习 3：规划接下来十二周 {#exercise-03}

该示例选择工具与库路线。每个四周增量都会交付可用边界，并以能缩小范围的评审结束。

### 第 1–4 周：在不改变语义的前提下升级清单脚本 {#weeks-01-04}

**成果：** 一个带 `Manifest.Core`、薄 CLI 与已发布可执行程序的 `net10.0` 控制台项目，保持清单脚本的 schema 版本 1。

工作包括：

- 把清单条目、渲染、规划结果与路径规范化移入有顺序的 `.fs` 模块；
- 把文件系统与控制台效果留在窄函数后；
- 为渲染添加基于示例的测试，并为退出 `0`、`1`、`2` 添加进程级测试；
- 在 Windows 与 Linux/macOS 临时目录测试分隔符、支持时的链接和输出排除；
- 发布依赖框架的产物，并在源码树外运行；
- 只有用户需要时才把脚本保留为小型兼容启动器，否则记录新命令。

重读第 9、16–18、21、26、28 与 30 章。不使用新的运行期包。真实边界是文件系统与进程 CLI。诊断记录命令、退出、stderr 类别、SDK、OS 与输出哈希。

评审问题：“是否有任何无效参数或文件系统失败能产生部分目标或成功退出？”如果项目增加了仪式，却没有改善测试、分发或锁定行为，就逆转。

### 第 5–8 周：增加版本化排除与依赖证据 {#weeks-05-08}

**成果：** schema 版本 2、练习 1 的显式排除语义、仍可读取版本 1 清单，以及一项已锁定解析器决策。

工作包括：

- 分开建模 `ManifestV1` 与 `ManifestV2`，并定义一条单向升级；
- 把规范化排除规则加入期望状态，让 `write`/`check` 共享一个规划器；
- 在添加任何包前执行练习 2 的解析器试验；
- 若采用包，提交精确包与闭包锁，并附还原审计证据；
- 在有界生成器内对排序、重复规则与渲染/解析稳定性执行模糊或属性测试；
- 增加迁移夹具，并在不覆盖的前提下拒绝未知未来 schema 版本；
- 在并行化前，针对代表文件树测量遍历与哈希。

重读第 10–15、27–31 与 37 章。包预算是一个 CLI 解析器，glob 包为零，除非匹配器试验证明需要。真实边界是 schema 兼容性与跨平台匹配。

评审问题：“版本 2 能否解释每个省略文件，并在不悄悄重解释的情况下保留版本 1 产物？”如果解析包的适配器与图超过它替代的行为，就移除它。

### 第 9–12 周：分发并运维工具 {#weeks-09-12}

**成果：** 由第二个夹具仓库消费的仓库本地工具或有版本可执行程序，具备可复现还原/构建、发布说明与回滚。

工作包括：

- 根据安装需求选择本地工具或普通发布可执行程序；
- 固定工具清单或产物版本，并测试从获准来源执行干净机器还原；
- 增加可选结构化 JSON 诊断，同时把面向人的 stderr 分开；
- 为大型扫描定义取消与最大支持文件数/输出大小；
- 构建未签名本地包/feed 夹具，因此不需要专有账号；
- 若发布策略要求，则生成 SBOM 或依赖清单，但不把它单独称为来源证明；
- 测试从上一命令升级并回滚；
- 请一位无上下文评审者只凭文档复现一个成功与一个清单过期失败。

重读第 20–24、27、30–32、38 与 45 章。包预算仍是获准解析器；每个新包都需要独立采用记录。真实边界是安装、来源信任、取消与兼容性。

评审问题：“新贡献者能否在没有私有机器知识的情况下还原、验证、升级、诊断并移除该工具？”若不能，就缩小分发目标或明确缺失所有权。

### 高级特性预算 {#advanced-budget}

三个增量都不需要 quotations、SRTP、灵活类型或自定义 byref。普通记录、联合、函数、效果处接口、用于取消的 task，以及数组/流已经足够。

只有性能分析显示边界复制占主导，且能证明同步生命周期时，才考虑 Span。只有多个具体算法真正需要一项成员约束抽象时，才考虑 SRTP。只有产品开始消费或生成表达式树时，quotations 才有意义。灵活类型可能出现在库签名中；决定是否暴露它前先正确识别。

这种克制是计划的一部分，而不是缺少雄心。学习目标是交付越来越可信的 F#，再在系统给出理由时深入某项语言特性。

## 评审清单 {#review-checklist}

- 模式与 CLI 语义是否在实现前写明？
- `write` 与 `check` 是否共享一个期望状态规划器？
- schema、路径、顺序、编码与大小写规则是否稳定且经过测试？
- 链接、输出文件、不受信任输入与破坏性目标策略是否显式？
- 研究到的包事实是否带日期，并同已执行仓库证据分开？
- 锁是否覆盖应用闭包，CI 是否强制锁定还原？
- 包专属类型能否在一个适配器处移除？
- 每个四周增量是否以可运行产物和可证伪评审问题结束？
- 高级特性是否由观察到的约束证明，而不是课程清单推动？
