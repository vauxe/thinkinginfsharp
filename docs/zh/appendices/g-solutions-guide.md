# 附录 G：练习与答案使用指南 {#overview}

每道练习的答案都放在题目后面，默认折叠。请先独立作答并写下预期，再展开答案比较思路。如果题目还要求解释类型、副作用、失败或资源归属，只得到相同输出还不算完成。

## 展开答案之前 {#before-opening}

1. 用自己的话重述必需行为与明确限制。
2. 运行代码前，预测重要类型、输出、失败与副作用顺序。
3. 运行最小的相关命令；保留意外诊断，不要盲目把代码改成书中答案。
4. 解释自己的答案为什么满足任务，再比较决策而不是行数。

## 三类练习 {#exercise-kinds}

| 类别 | 可以直接检查什么 | 哪些地方允许变化 |
|---|---|---|
| 固定行为题 | 必需值、类型、输出顺序、诊断或测试 | 名称与实现可以不同，但必须保留完整契约 |
| 诊断题 | 复现命令、第一条相关证据、根因与修复 | 多种修复都可能编译，只有保留预期语义的方案才合格 |
| 开放设计题 | 约束、不变量、边界、失败策略与验证计划 | 表示、库、架构和发布方式可以随明确取舍变化 |

## 评审开放设计 {#review-rubric}

高质量的开放题答案应当：

- 覆盖每项必需输入、输出、失败与非目标；
- 清楚表示有效状态，并在明确边界拒绝无效输入；
- 说明 I/O、时间、可变状态、资源与取消由谁负责；
- 让公共 API 对调用方自然可用，不泄漏内部表示；
- 区分已经执行的检查、资料审阅和尚未验证的方案；
- 比较一种可信替代方案，并写明停止或撤销选择的条件。

不同答案只要保留书面约束、公开新增假设并验证关键风险，就可以接受。若你的方案更简单且证据不弱于书中方案，应反过来改进书中答案。

## 让主张与证据匹配 {#evidence}

| 主张 | 最低合适证据 |
|---|---|
| 类型关系或诊断 | 准确的 SDK/编译器命令，以及相关签名或诊断 |
| 纯行为或不变量 | 包含边界或反例的聚焦示例测试或属性测试 |
| 资源、异步、并发或互操作行为 | 使用确定性协调与清理的真实边界测试 |
| 框架、包或架构选择 | 书面约束、权威资料审阅、聚焦试验与回滚条件 |

不要把未运行的平台检查报告为通过，不要隐藏相关警告、泄漏机密、静默修改公共 API，也不要用定时等待证明并发行为。
