# 中文正文易读性审校计划

## 目标

完整审校 `docs/zh/part-01` 至 `docs/zh/part-07` 的第 1–45 章，降低初学者的理解成本，同时保持技术含义、代码示例、章节结构和中英文页面对应关系不变。

## 审校标准

- 优先把生硬或宽泛的说法直接换成常用词语，不用追加解释来补救措辞。
- 只有无法安全替换的必要术语，才在首次出现时用一句短定义说明。
- 拆分同时承载多个限制、因果或转折的长句。
- 减少抽象名词连续堆叠，直接写明谁做什么、在什么条件下得到什么结果。
- 优先使用自然、直接的中文，修正生硬直译；技术名词保留通行译法和必要英文。
- 让代词和“这里”“这样”“该项”等指代有明确对象。
- 保留精确限制，不以通俗为由把“可能”“仅在……时”等边界改成绝对结论。

## 不在范围内

- 不修改英文原稿、练习答案、附录和站点代码。
- 不改变代码块、命令、API 名称、锚点或章节组织。
- 不新增技术主张；遇到技术含义不清时，以英文对应段落和已有上下文校准。

## 实施顺序

每批依次执行“完整阅读 → 标记理解障碍 → 小范围改写 → 对照复核”。

1. 第 1–5 章
2. 第 6–10 章
3. 第 11–15 章
4. 第 16–20 章
5. 第 21–25 章
6. 第 26–30 章
7. 第 31–35 章
8. 第 36–40 章
9. 第 41–45 章

每完成三个批次运行一次 `npm run check:book`，确认双语标题结构与共享代码块仍然一致。全部完成后运行 `npm run check`，覆盖主题测试、书稿检查和站点构建。

## 验收标准

- 45 章均已完整审校，没有只靠关键词批量替换。
- 每处修改都能说明它消除了哪一种理解障碍。
- F#、.NET 和领域建模含义没有因简化而改变。
- `npm run check` 通过。
- 最终交付按章节列出主要修改类型和仍需作者判断的措辞。

## 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 简化后损失技术精度 | 对照英文原稿、上下文和代码示例复核 |
| 中文改写破坏双语结构 | 不改锚点和代码块；分批运行 `check:book` |
| 大范围改动难以评审 | 每批限制为 5 章，逐批检查差异 |
| 不同章节术语不一致 | 记录重复术语，最终做一次跨章一致性检查 |

## 第二轮：正确性、完整性与简洁性复核

### 目标

在第一轮易读性改写的基础上，再次完整阅读第 1–45 章。逐章确认中文准确传达英文原稿，代码示例能够支持正文结论，章节承诺的知识点没有遗漏，措辞简洁且适合初学者。

英文正文和练习答案仍不做普通措辞改写；若发现版本事实错误，则同步修正相关中英文正文与答案，避免同一书内出现冲突。

### 复核方法

1. 先运行书稿检查，建立当前结构、标题和代码块一致性的基线。
2. 按第 1–15、16–30、31–45 章分三批对照中英文正文；每批记录并修正事实错误、内容缺口、前后矛盾和表达障碍。
3. 对可能随版本变化的 .NET、框架、工具和包信息，仅采用官方文档、官方仓库或官方包页面核验。
4. 每批完成后检查差异和书稿结构；全部完成后复核跨章术语、链接、章节目标与总结。
5. 对候选修改进行一次独立的质疑式审阅，再处理其指出的有效问题。
6. 最后运行完整检查和站点构建。

### 第二轮验收标准

- 第 1–45 章均与英文原稿、代码示例和相邻章节完成对照复核。
- 没有已知事实错误、章节目标遗漏、正文与代码矛盾或会误导初学者的绝对化表述。
- 句子直接说明主体、动作和条件；不靠增加解释掩盖生硬措辞。
- 版本敏感信息有官方依据，且时间口径写清楚。
- 双语标题结构、共享代码块、内部链接和站点构建均通过检查。
