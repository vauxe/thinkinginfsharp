# 实施计划：F# 思维 / Thinking in F#

状态：已批准，实施中
日期：2026-08-24
依据：[已批准规格](../specs/book-site.md)

> 本文件定义实施顺序与质量门。用户已批准计划；实现按 `tasks/todo.md` 的顺序小步推进。

## 1. 交付结果

交付一个无需后端服务的中英双语静态书站。两种语言拥有相同的信息架构、概念深度、示例、练习和答案；所有 F# 有效代码来自同一份可执行源码。首版以 F# 10、.NET 10 LTS 和 VitePress 1.6.4 为基线，核心内容覆盖语言、类型建模、程序结构、副作用、异步并发、.NET/C# 互操作、工程质量、贯穿项目及有边界的生态地图。

计划包含：

- 45 个双语章节、双语前言和 8 个双语附录；
- 每章共享的可验证 F# 示例、练习和答案；
- 可运行的活动预约系统及 JSON/C#/并发/持久化契约证据；
- ASP.NET Core、数据与类型提供器、Fable、云与 Aspire、Avalonia、Unity 和自动化的代表性示例；
- 双语语义一致性、内容链接、F# 构建测试和站点构建质量门。

计划不包含：

- 在线账号、评论、遥测、付费搜索或动态后端；
- 对第三方生态的百科式穷举；
- 完整商业支付、通知或认证系统；
- 首版中的类型提供器创作、编译器服务或 Unity 游戏教程。

## 2. 已确认约束与实施假设

1. 工作区目前不是 Git 仓库。计划获批后，F01 会在当前目录初始化 Git；不会配置远端、推送或发布。
2. 网站依赖安装需要访问包注册表；只在 F01 获批后执行并锁定 `pnpm-lock.yaml`。
3. 核心示例统一以 `net10.0` 构建；Unity 插件是独立的 `netstandard2.1` 目标。
4. `/zh/` 与 `/en/` 是完整对等版本；根路径只提供中立的语言入口。
5. 每个事实性语言或生态主张优先依据官方文档，并记录验证版本与复核日期。
6. 普通章节保持小切片；多项目、跨语言或平台示例拆成独立示例任务和正文任务。
7. Unity 自动门只验证 F# 插件编译与装配结构；导入、IL2CPP 和代表性 Player 构建按规格保留为明确版本的人工门。
8. 计划获批后，每个通过验证的小任务形成一个原子本地提交；不配置远端、不推送、不打标签、不发布，这些外部动作需要另行明确授权。计划文件本身当前不提交。

## 4. 任务切片契约

### 4.1 普通章节任务

一个普通章节任务最多修改以下 5 个主要文件：

1. `docs/zh/part-NN/ch-NN-slug.md`；
2. `docs/en/part-NN/ch-NN-slug.md`；
3. `docs/zh/solutions/ch-NN-slug.md`；
4. `docs/en/solutions/ch-NN-slug.md`；
5. `examples/scripts/chNN-slug.fsx`。

若示例需要多个项目、C# 调用者、测试夹具或平台工程，则先完成独立的 `E*`、`K*` 或 `X*` 示例任务；对应 `B*` 正文任务只负责双语正文与答案。

每个章节任务共同满足：

- frontmatter、`translationKey`、章节号、示例号和练习号成对；
- 两种语言语义对等，但各自使用自然表达，不逐句机械翻译；
- 遵循“问题 → 模型 → 推导 → 可运行示例 → 常见错误 → 练习 → 小结”；
- 至少一个理解练习；核心章另有修改或设计练习及答案；
- 代码由共享源文件引入，不在中英文正文中复制成两份；
- 新概念不把后续章节知识当作未说明的前提；
- 事实主张有官方来源，示例在锁定版本上通过；
- 通过 `pnpm check:parity`、`pnpm check:content`、相应 F# 检查和 `pnpm build`。

### 4.2 示例工程任务

每个示例工程任务共同满足：

- Release 构建警告即错误，输出可重复；
- 时间、随机数、区域设置、文件路径和外部依赖受控；
- 可执行示例测试成功路径及至少一个关键失败或边界路径；
- 预期失败代码只能位于 `examples/expected-errors/`，并断言诊断编号；
- 依赖版本写入项目文件或锁文件，不在正文中使用模糊的“最新版”；
- 通过聚焦 `dotnet build/test/fsi` 和 `pnpm check:examples`。

### 4.3 检查点

每完成一个检查点：

- 运行完整 `pnpm test`；
- 检查工作区差异只包含本阶段范围；
- 在提交前检查差异与敏感信息；每个已验证任务保持为单一逻辑提交，不把格式化与行为改动混在一起；
- 记录事实复核、人工审阅和未解决风险；
- 只有前一阶段质量门为绿，才进入下一阶段。

## 6. 实施阶段

### 阶段 0：基础与可执行质量门（F01–F07）

目标：在写大规模正文前，让站点、双语契约和 F# 示例从第一天即可验证。

- F01：初始化本地 Git 与锁定 Node、pnpm、.NET 工具链；
- F02：建立最小 VitePress 静态站及稳定命令；
- F03：建立中立入口、双语路由、语言切换和最小可访问主题；
- F04：定义 frontmatter、页面身份、术语和共享代码引用契约；
- F05：实现双语集合、元数据、链接、锚点、术语与代码引用检查；
- F06：建立 `ThinkingInFSharp.slnx`、F# 测试骨架和警告即错误策略；
- F07：实现脚本、项目、测试、契约和预期诊断的统一示例检查入口。

检查点 C0：空内容骨架执行 `pnpm test` 成功。

### 阶段 1：纵向试点与第一部分（B01–B06、K01）

先完成 B01 的中英正文、共享 FSI 示例、练习答案、导航和生产构建，验证整条作者工作流。试点通过后再完成第 2–6 章。

K01 把第一部分的预约输入、基本转换、管道、递归与折叠汇成纯脚本，但不提前引入领域联合类型或 I/O。

检查点 C1：

- 6 章双语内容和答案成对；
- 所有脚本独立执行且输出稳定；
- 初学者能沿快速路线完成第一部分；
- `pnpm test` 与移动端/语言切换人工冒烟通过。

### 阶段 2：第二部分——类型建模（B07–B12、K02）

按元组/记录 → 联合类型 → `option`/`Result` → 递归类型 → 泛型约束 → 私有表示的顺序完成。K02 建立预约系统的领域类型、智能构造函数与不变量测试。

专项证据：

- 结构相等、结构比较、引用身份、哈希相等不混为一谈；
- `Some null` 被明确视为 .NET 边界风险；
- 泛化、值限制、相等/比较约束和度量单位各有可执行例子；
- 非法领域状态不能绕过公开 API 构造。

检查点 C2：类型建模练习、K02 单元测试和全站质量门通过。

### 阶段 3：第三部分——组合与结构（B13–B18、E16–E17、K03）

完成管道 API、集合选择、活动模式、项目结构、签名与封装、显式工作流组合。E16–E17 先提供多文件顺序与签名边界的编译证据；K03 用普通函数组合预约验证，并同时演示失败短路与错误累积。

专项证据：

- `seq` 的惰性、副作用和重复枚举由测试观察；
- `Map`/`Set` 与哈希集合的键约束和选择依据明确；
- 项目启用 nullable 分析所需的最小设置；
- 不暗示 FSharp.Core 内置 `Result` 或验证计算表达式。

检查点 C3：多文件构建、签名边界、集合行为和工作流测试通过。

### 阶段 4：第四部分——副作用、异步与并发（E19、B19–B24、K04）

E19 先固定 .NET 空值契约，再进入依赖隔离、异常与资源、`Async`/`Task`、取消/超时和并发。K04 给预约工作流增加异步端口接口和确定性替身。

专项证据：

- `T | null`、`Nullable<T>`、`option` 的转换及限制有契约测试；
- `Async<'T>` 与 `task {}` 的启动时机由可观察测试证明；
- 取消令牌显式传播，并区分取消操作与放弃等待；
- 成功、故障、取消路径都验证同步/异步资源释放；
- 竞争和缓存示例不靠不稳定计时断言。

检查点 C4：异步、取消、释放、竞争测试和全站质量门通过。

### 阶段 5：第五部分——互操作与工程质量（E25、E27–E32、B25–B32、K05）

对象模型、深层 .NET 边界和普通测试可使用小型共享示例；跨语言、性质测试、预期诊断、测量和应用装配使用独立 `E*` 任务。

- E25：对象、接口、对象表达式、扩展和结构体样例；
- E27：F# 库 + C# 调用者的公共 API 契约；
- E28：单元、替身与边界测试样例；
- E29：FsCheck 性质测试；
- E30：预期诊断、格式化与可复现构建样例；
- E31：固定环境下的基准与剖析样例；
- E32：端口、配置、生命周期和最小可观测性宿主；
- K05：为贯穿项目补齐单元、性质、替身和 C# 友好边界。

检查点 C5：双向互操作、性质测试、诊断、格式化和基线测量证据通过；不把微基准结果泛化为语言结论。

### 阶段 6：第六部分——贯穿项目装配（K06–K12，含 K08a/b、K12a/b；B33–B38）

按业务模型、纯工作流、适配器、Web 边界、持久化一致性、集成与发布证据分步装配：

- K06：稳定领域模型、命令、事件和公开模块；
- K07：纯预约工作流与验证；
- K08a：边界 DTO、JSON 映射和配置；
- K08b：无需外部账号的本地持久化；
- K09：支付/通知确定性替身及生命周期；
- K10：ASP.NET Core Web API、取消和机密配置边界；
- K11：原子容量、幂等、重试、部分失败和重启恢复；
- K12a：集成测试和 C# 契约客户端；
- K12b：结构化诊断、运行说明和发布脚本。

每个 `K*` 示例任务先提供通过的代码证据，对应 `B33–B38` 再解释设计推导，避免正文描述尚不存在的系统。

检查点 C6 必须覆盖：

- 两个竞争预约不会超卖；
- 重复请求标识不重复产生副作用；
- 失败后重试行为明确；
- 进程重启后持久状态仍正确；
- JSON 契约和 C# 客户端兼容；

## 8. 风险控制

| 风险 | 早期信号 | 控制措施 |
| --- | --- | --- |
| 双语范围导致长期半成品 | 单语页面或占位页开始累积 | 中英正文、答案与示例作为一个不可拆完成单元 |
| 内容“全面”演变为百科 | 单章承担多个主要抽象或生态清单不断增长 | 坚持能力证据矩阵；发散内容移至带边界的附录/继续学习 |
| 示例与正文漂移 | 正文出现无法定位到源码的代码块 | 单一代码来源和内容检查器阻止合入 |
| F# 事实被 C# 心智误导 | 以类层次、null 或立即执行解释所有构造 | 官方来源复核 + 无上下文 F# 专家审阅 |
| 异步测试不稳定 | 使用任意 sleep 或只断言耗时 | 使用门闩、可控时钟/端口和确定性调度证据 |
| 生态版本快速变化 | “最新版”、未锁包或死链 | 记录版本、复核日期和升级矩阵；生态示例隔离 |
| 贯穿项目过度设计 | 强制云账号、消息总线或额外服务 | 保持本地真实持久化，外部端口用确定性替身 |
| Unity 验证被误报 | 只有类库构建却声称 Unity 可用 | 自动与人工门分列，记录编辑器补丁和 Player 证据 |
| 计划任务过大 | 单项同时改正文、多个项目与全站配置 | 超过 5 个主要文件时拆为代码、正文或装配任务 |

## 9. 完成定义

只有同时满足以下条件，项目才算完成：

- `tasks/todo.md` 中所有任务和检查点均完成；
- `pnpm install --frozen-lockfile && pnpm test` 在干净检出中成功；
